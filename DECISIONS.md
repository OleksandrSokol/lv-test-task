# Решения

## Главное

**Вебхук обрабатывается синхронно, письма — в очереди.** В одной транзакции: запись события в inbox,
применение снимка заказа, история статусов. Ответ — за миллисекунды, а API сразу видит новое состояние.
Если что-то упало, транзакция откатывается, мы отвечаем 5xx, и маркетплейс сам доставит событие повторно —
отдельный механизм ретраев не нужен. Письма уходят job'ом после коммита (`afterCommit`), их сбой
не влияет на ответ маркетплейсу.

**Идемпотентность — уникальный `event_id` в inbox (`webhook_events`).** Вставка через `createOrFirst`:
повтор, в том числе параллельный, упирается в уникальный индекс, ждёт коммита первого и получает
`duplicate` (200) без побочных эффектов. Отклонённые запросы (401, 422) в inbox не попадают — их повтор
обрабатывается как новый. Сырое тело запроса хранится байт в байт (`raw_body`) — для разбора спорных случаев.

**Подпись** — HMAC от `$request->getContent()`, а не от пересобранного JSON; `hash_equals`;
окно ±5 минут по `X-Webhook-Timestamp`. Подпись проверяется до валидации тела.

**Свежесть — по `updated_at` снимка, а не по статусу.** Статус не монотонный (ручная коррекция
delivered → shipped), поэтому применяется снимок строго новее сохранённого. Снимки одного заказа
применяются по очереди под блокировкой строки заказа; первый снимок нового заказа — тоже через
`createOrFirst`. Устаревший снимок состояние не меняет, но пополняет историю: он может быть единственным
свидетелем статуса, в котором заказ уже не находится. Моменты истории — из данных маркетплейса
(`paid_at`, `cancelled_at`, `updated_at`), не `now()`.

**Письма: «не дважды» и «не противоречит состоянию».** Каждое письмо — максимум одно на заказ
(уникальный индекс `order_id + template_key` в журнале писем). Письмо ставится, только когда снимок
применён и статус сменился, и только если не противоречит текущему статусу: `shipped`/`delivered`
не противоречат «оплачен», `cancelled` — только «отменён». Перед отправкой job перечитывает письмо
под блокировкой; если заказ тем временем отменили, ещё не ушедшее «оплачен» снимается (`skipped`).

**Конкурентность проверена тестом с настоящей параллельностью** (`tests/Feature/Scenarios/ConcurrentDeliveryTest`):
две доставки из двух процессов (`pcntl_fork`) со своими соединениями к базе, стартующие одновременно.

**PostgreSQL**: `timestamptz` (моменты с любым смещением сравниваются корректно), функциональный индекс
по `lower(customer_email)`, `jsonb`, транзакционные миграции. **Redis** — очередь и кэш: воркер
не зависит от таблиц базы и стартует до миграций.

**API** — стандартные API Resources и пагинация Laravel (`data/links/meta`), как в `openapi.yaml`;
суммы — `numeric(12,2)` и строка `"1499.90"`, даты — ISO 8601 с тем же моментом, что у маркетплейса.
Ошибки `api/*` — всегда JSON, тексты — на русском.

**Модули** (`app/Modules/*`): `Marketplace` (приём), `Order` (заказы, API, правило писем), `Notification`
(шаблоны, журнал, отправка), `Core` (журнал действий), `User`. **Журнал действий** пишется слушателем
доменных событий после коммита: откат транзакции не оставляет записей, а в админке видно, почему письмо
не ушло или почему снимок признан устаревшим.

**Админка — Filament**: список, фильтры, карточка, журналы — из коробки, минимум своего кода;
отдельный фронт для нескольких экранов был бы лишним. Заказы и журналы — только чтение; редактируются
шаблоны писем и пользователи. Даты в админке — по Москве, в API — UTC.

## Вопросы и допущения

| Вопрос бизнесу / маркетплейсу | Допущение |
|---|---|
| Время в событиях — с точностью до секунды. Что делать, если два снимка заказа пришли с одинаковым `updated_at`? | Состояние заказа меняет только снимок строго новее сохранённого. Снимок с тем же временем состояние не меняет, но его статус попадает в историю |
| Пришло событие незнакомого типа (маркетплейс добавил новый). Применять ли снимок заказа из него? | Нет. Отвечаем 200, сохраняем событие со статусом `ignored`, заказ не трогаем |
| События пришли не по порядку: `shipped` раньше `paid`. Отправлять ли письмо «оплачен», когда `paid` придёт позже? | Нет. Опоздавший снимок старше текущего состояния — он не меняет заказ и писем не запускает. Покупатель получит только «передан в доставку» |
| Как понять, что отменённый заказ «был оплачен» (тогда в письме об отмене — про возврат денег)? | Заполнен `paid_at` в снимке, даже если статуса `paid` мы не видели |
| Статус исправили вручную (delivered → shipped). Слать ли «передан в доставку» ещё раз? | Нет. Каждое письмо уходит покупателю не больше одного раза за заказ |
| Покупатель сменил email между событиями. На какой адрес слать письмо? | На email из текущего состояния заказа в момент, когда письмо ставится в очередь |
| Итог `total` не равен сумме позиций, доставки и скидки. Кому верить? | Маркетплейсу: сохраняем и показываем `total` как есть, не пересчитываем |
| Подпись верная, но тело не по формату (нет полей, неверная сумма или дата). Что отвечать? | 422 и событие не сохраняем: после исправления маркетплейс пришлёт его снова и оно обработается как новое |
| Маркетплейс начнёт присылать новую валюту (сейчас RUB, USD, EUR). Предупредит ли заранее? | Незнакомая валюта — 422. Добавить её — одна строка в `CurrencyEnum`, без миграции |
| Что API отвечает на `per_page` больше 100 или незнакомый `status` в фильтре? | 422: границы заданы контрактом `openapi.yaml` |
| Фильтр `email` в API ищет по части адреса? | Нет: точное совпадение без учёта регистра. В админке — обычный поиск по части адреса |

## Что дальше

- Outbox для писем вместо job: письмо гарантированно уходит, даже если упала постановка в очередь.
- Повторная отправка писем со статусом `failed` (сейчас — 3 попытки, затем статус и причина в журнале).
- Очистка inbox и журналов по сроку; повторы доставки сейчас видны только в журнале действий.
- Алерты и метрики: рост `stale`, 401, `failed`-писем, время обработки вебхука.
- Отдельный воркер и очередь для писем; нагрузочный тест параллельных доставок.
- При росте нагрузки — обработка вебхуков в очереди: эндпоинт только проверяет подпись, пишет событие
  в inbox и сразу отвечает 200, а снимок применяет воркер. Inbox и правило свежести это уже позволяют;
  цена — API видит изменение с задержкой, а сбой обработки надо ретраить самим, а не через маркетплейс.

Всё, что требует задание, сделано; админка (по желанию) — тоже.
